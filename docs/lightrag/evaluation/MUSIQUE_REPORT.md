# MuSiQue 多跳基准：现有混合检索与 GraphRAG 对比

本实验用于决定 GraphRAG（LightRAG）是否值得继续投入。协议和判定规则在任何模型调用之前冻结，见
[`evaluation/musique_multihop/protocol.json`](../../../evaluation/musique_multihop/protocol.json)。
逐题检索、答案、用量和统计结果存放在 [`musique-run1/`](musique-run1/)。

**结论：按冻结规则判为“不确定（inconclusive）”。** GraphRAG 比现有混合检索找到了更完整的证据，
但探索性分析表明，这部分优势来自 LightRAG 的向量检索，并非来自知识图谱本身。图谱在检索上没有
增益，代价是约 20 倍的查询延迟，以及每段资料约 2600 token 的建索引开销。

## 设置

- **题目与语料**：MuSiQue-Ans v1.0 dev，CC BY 4.0。两个 HuggingFace 镜像下载的文件 SHA-256 一致，
  即 `15fa6379…abf3b`。按固定种子分层抽取 100 题：2 跳 40 题、3 跳 30 题、4 跳 30 题。
  每题的 20 段材料（包含证据段与干扰段）去重后合并为一个知识库，共 1770 段；每段即一份文档、一个分块。
- **对比方法**：
  - 现有混合检索 `hybrid_rrf`：BM25 + 向量 + RRF，不启用 rerank，与生产一致。
  - LightRAG `mix`：生产所用模式，`top_k=40`、`chunk_top_k=20`。
  - 诊断臂 LightRAG `naive`：LightRAG 自身的纯向量检索，不使用图谱。
- **模型**：
  - 抽取：`Pro/deepseek-ai/DeepSeek-V3.2`，即生产 `KNOWLEDGE_*` 配置。
  - Embedding：两种方法都用 `BAAI/bge-m3`。
  - 回答：生产知识问答配置 `Qwen/Qwen3.8-27B`，关闭思考，temperature 0。
  - 所有模型都经 SiliconFlow 调用。
- **回答方式**：每题每臂单次调用，取检索结果的前 10 段作为上下文，只给文本分块。这与生产一致：
  `knowledge_agent` 不把实体和关系传给模型。
- **运行环境**：两种方法各在自己的生产依赖环境中运行。主应用与知识库服务锁定的 `openai` 版本不同。

## 与冻结协议的偏差

这些偏差都没有改动协议文件，全部记录在此：

1. **Embedding 统一为 bge-m3**。主应用生产配置的 `bge-large-zh-v1.5` 只支持中文，用在英文题上会不公平地
   削弱基线。协议事先写明了这一点。
2. **回答温度设为 0**，而生产为 0.7，以保证结果可复现。这一点同样事先写明。
3. **限流重发**：
   - 回答阶段首轮以并发 8 运行，400 次调用中有 288 次收到 HTTP 429 限流。429 表示请求被拒，
     没有产生任何模型输出，因此重发它不算“重新采样”。
   - 做法是：保留首轮已作答的 112 条，只重发这 288 条，并发改为 2，并对 429 做退避。
   - 结果：共 115 条记录重试过 1 次，没有一条重试超过 1 次，最终 0 失败。
   - 已产生答案的调用一律没有重复。首轮原始记录保留在 `answers_run1_with_429.jsonl`。
4. **索引中断与恢复**：
   - SiliconFlow 余额耗尽（HTTP 402）导致索引在第 747 段处中断。充值后从断点恢复。
   - 恢复时发现 LightRAG 1.5.7 的自动扫描不会重试 FAILED 状态的文档，只有手动独占重置才会。
     因此把 139 段失败文档删除后重新插入。这些文档在写入图谱之前就已失败，删除不会移除任何已有图谱数据。
   - 最终 1770 段全部 `processed`。脚本在仍有未入库文档时会拒绝进入查询阶段。
   - 进入查询前核对了缓存类型，只有 `extract` 和 `summary`，没有 `keywords`，说明中断没有提前产生查询缓存，
     不会让查询延迟显得偏快。
5. **部分成本数据缺失**：
   - 第一个会话在写出用量前被终止，前 747 段的 token 用量**未知，不按零计**。
   - 第三个会话的索引耗时被一个计时变量遮蔽 bug 覆盖，同样未知。该 bug 已修复。
   - 查询延迟单独计时，不受这个 bug 影响。

## 预注册指标结果

| 指标（n=100） | 混合检索 | LightRAG mix | LightRAG naive |
| --- | ---: | ---: | ---: |
| Recall@5 | 47.6 | 52.9 | 58.9 |
| Recall@10 | 61.9 | 66.2 | 70.7 |
| Recall@20 | 76.6 | 77.2 | 79.4 |
| 前 10 段含全部证据 | 25% | 37% | 39% |
| 回答 EM | 28.0 | 33.0 | 33.0 |
| **回答 F1（主终点）** | **38.9** | **44.1** | 43.5 |
| 查询延迟 p50 / p95 | 0.15 / 0.31 s | 4.8 / 17.3 s | 0.24 / 0.46 s |

与混合检索的配对比较，区间为配对 bootstrap 95%，检验为精确 McNemar：

| 比较 | F1 差值 | Recall@10 差值 | 前 10 段证据齐全 | EM |
| --- | --- | --- | --- | --- |
| mix − 混合 | **+5.3 [−2.6, +13.3]** | +4.3 [−0.7, +9.0] | 15 胜 3 负，p=0.008 | 11 胜 6 负，p=0.33 |
| naive − 混合 | +4.6 [−3.9, +13.6] | +8.8 [+4.1, +13.2] | 18 胜 4 负，p=0.004 | 12 胜 7 负，p=0.36 |

**判定**：主终点均值为 +5.3，达到 +5 的门槛，但 95% 区间下界为 −2.6，不大于 0，所以不是“投入”。
区间上界 +13.3 不低于 +2，所以也不是“收缩”。按规则判为“不确定”，需要结合检索终点和成本来决定。

按跳数拆分（描述性，未单独检验），格式为 F1 / 前 10 段证据齐全率：

| | 2 跳 | 3 跳 | 4 跳 |
| --- | --- | --- | --- |
| 混合检索 | 53.2 / 50.0% | 39.8 / 16.7% | 19.0 / 0.0% |
| LightRAG mix | 60.8 / 67.5% | 45.5 / 30.0% | 20.6 / 3.3% |
| LightRAG naive | 53.5 / 65.0% | 51.1 / 36.7% | 22.5 / 6.7% |

## 探索性分析（未预注册，仅作解释）

| 比较 | 结果 |
| --- | --- |
| **图谱本身的贡献**：mix − naive | Recall@5 −6.0 [−9.0, −3.3]；Recall@10 −4.4 [−7.2, −1.7]；前 10 段证据齐全 2 胜 4 负，p=0.69；F1 +0.7 [−5.7, +6.9] |
| **把图谱事实交给回答模型**：mix+实体关系 − mix | F1 +4.2 [−1.4, +9.9]；EM 6 胜 4 负，p=0.75 |
| mix+实体关系 − 混合检索 | F1 +9.4 [+1.0, +17.7]，所有回答臂中唯一 95% 区间排除 0 的一项；4 跳 F1 为 30.0，混合检索为 19.0 |

## 解读

1. **检索更完整，但功劳不在图谱。** mix 与 naive 使用同一个 LightRAG 索引，差别只在是否用图谱。
   加上图谱后，Recall 反而**显著下降**，答案质量没有变化。GraphRAG 相对现有检索的优势，
   实际上等同于“纯向量检索比 BM25+RRF 更适合这类题”。
2. **现有混合检索在这里吃亏，原因在 BM25。** 已核对，英文分词正常。MuSiQue 的干扰段刻意与问题共享词汇，
   BM25 会把这些词面相似但不相关的段落排上来，等权 RRF 又把它们带进前列。
   这指向一个比 GraphRAG 便宜得多的改进方向：调整融合权重，或让向量检索占主导。
   不过本实验没有验证这一点，而且中文材料的情况可能不同。
3. **图谱真正可能有用的地方，生产目前没有使用。** 把实体和关系描述交给回答模型后，
   F1 相对混合检索的提升是唯一显著的一项，4 跳题上尤其明显。但相对仅用分块的 mix 并不显著，
   因此只是一个值得验证的线索，还不能当作结论。
4. **成本**：
   - 建索引：每段约 1930 输入 + 690 输出 token。已记录的会话共 1161 次调用、284 万 token；
     另有 747 段的用量未知，按冒烟测试估算约 196 万。
   - 索引时间：全部 1770 段的墙钟时间约 2 小时，并发 16。
   - 查询：p50 慢约 30 倍，p95 慢约 55 倍。

## 建议

- **暂停 GraphRAG 的并发与规模化投入**，包括读锁移除六步、连接池等。现有证据不支持图谱在检索上带来增益。
- **先做两个便宜的验证**：
  - 在主应用混合检索中试验向量主导或加权 RRF。
  - 如果继续保留 GraphRAG 作为可选功能，试验把实体和关系交给回答模型，并在中文材料上复核。
- GraphRAG 维持**可选、默认关闭**，这是现状。是否移除，要等中文复核结果出来再定。

## 局限

- 英文题，仅一个数据集，n=100；按跳数的分组结果是描述性的。
- 回答是单次调用，不是生产 Autonomous 的多轮工具执行。
- 未覆盖 GraphRAG 声称擅长的全局性或主题性问题。
- 结果依赖所选模型（DeepSeek-V3.2 抽取、Qwen3.8-27B 回答、bge-m3）。
- 货币成本未估算，以 SiliconFlow 账单为准。

## 复现

```bash
python scripts/prepare_musique_benchmark.py <musique_ans_v1.0_dev.jsonl>   # 生成冻结样本，校验源文件哈希
python scripts/evaluate_multihop.py validate
# 主应用环境：
python scripts/evaluate_multihop.py retrieve-baseline --state <dir>
# 知识库服务环境，并设置 KNOWLEDGE_EVAL_DATABASE_URL 指向一次性 pgvector 数据库：
python scripts/evaluate_multihop.py retrieve-graph --state <dir> --parallel 16
python scripts/evaluate_multihop.py answer --state <dir> --concurrency 2
python scripts/evaluate_multihop.py score --state <dir>
```

归档的 `retrieval_graph.json.gz` 需要先解压，才能对归档结果重新打分。
